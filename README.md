# AI Task Manager

Учебный Telegram-бот для управления личными задачами на русском языке. Он создаёт,
показывает, завершает, переносит и удаляет задачи, понимает относительные даты и
присылает напоминания. Общаться с ботом нужно **в личном чате**.

Стек: Python 3.12, aiogram 3, PostgreSQL 16, SQLAlchemy 2 async + asyncpg,
Pydantic Settings, официальный Groq SDK, APScheduler 3, Docker Compose.
Модель по умолчанию — `openai/gpt-oss-20b`.

## Запуск

1. В Telegram откройте **@BotFather**, выполните `/newbot`, задайте имя и username.
   Полученный токен понадобится в `TELEGRAM_BOT_TOKEN`.
2. Создайте API-ключ в [Groq Console](https://console.groq.com/keys).
3. В каталоге `hse` скопируйте пример настроек:

   ```bash
   cp .env.example .env
   ```

4. Заполните `TELEGRAM_BOT_TOKEN` и `GROQ_API_KEY` в `.env`.
   Остальные значения подходят для Docker Compose:

   ```dotenv
   TELEGRAM_BOT_TOKEN=<токен от BotFather>
   GROQ_API_KEY=<ключ из Groq Console>
   DATABASE_URL=postgresql+asyncpg://postgres:postgres@postgres:5432/task_manager
   GROQ_MODEL=openai/gpt-oss-20b
   TIMEZONE=Europe/Moscow
   REMINDER_CHECK_MINUTES=1
   ```

   Ключи не входят в исходники или Docker image. `.env` исключён из Git.
   Переменные окружения имеют приоритет над `.env`.

5. Запустите:

   ```bash
   docker compose up --build
   ```

   PostgreSQL сначала проходит healthcheck. Бот создаёт таблицы и запускает polling.
   Откройте своего бота и отправьте `/start`.

Остановка: `docker compose down`. Задачи сохраняются в Docker volume.
Логи: `docker compose logs -f bot`. Запускайте только один экземпляр бота
с одним Telegram-токеном и одной базой: scheduler рассчитан на один процесс.
Пароль PostgreSQL в Compose предназначен для локального учебного запуска;
порт базы не публикуется на хосте.

### Запуск без Docker

Нужны Python 3.12 и доступный PostgreSQL. Создайте базу `task_manager`, укажите в
`.env` её адрес с драйвером `postgresql+asyncpg` (вместо хоста `postgres` укажите
адрес своего сервера, например `localhost`). Затем:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

## Использование

- `/start`, `/help` — справка без обращения к LLM.
- `/tasks` — активные задачи с ID, сроком и приоритетом, напрямую из БД.
- «Добавь задачу сделать лабораторную завтра в 18:00».
- «Добавь на завтра купить продукты и закончить лабораторную».
- «Что у меня завтра?».
- «Покажи важные задачи».
- «Я закончил лабораторную».
- «Перенеси лабораторную на пятницу в 15:00».
- «Сделай лабораторную важной».
- «Удали задачу купить продукты».

Если бот нашёл несколько задач, повторите действие с точным названием или ID:
«Заверши задачу с ID 12». Бот помнит последние пять обменов сообщениями каждого
пользователя, включая результаты инструментов. Поэтому после уточнения можно
ответить «18:00» или «вторую», не повторяя весь запрос. Сообщения одного
пользователя обрабатываются последовательно, история разных пользователей изолирована.
История хранится в памяти и очищается при перезапуске; для старого диалога
после очистки снова укажите задачу. Память ограничена 40 000 символов на диалог.
Кэш рассчитан на 1000 диалогов; при переполнении вытесняются самые старые
неактивные диалоги. Активные запросы дожидаются завершения, поэтому во время
их обработки лимит количества диалогов может временно превышаться.
Для расплывчатого времени, например «вечером», бот попросит точное время.
Задачи без срока сохраняются, но не создают напоминаний.

## Архитектура и tool calling

```text
Telegram → bot.py → llm_service.py → Groq
                          ↓ выбранный tool
                   task_service.py → repository.py → PostgreSQL
                          ↑ результат операции
                       Groq → ответ пользователю
```

Tool calling — модель возвращает имя функции и JSON с аргументами, например
`create_task(title="Лабораторная", deadline="2026-10-16T18:00:00+03:00")`.
Python проверяет имя инструмента, типы, длины, даты и права доступа, выполняет
операцию и передаёт результат модели сообщением `role="tool"` с `tool_call_id`.
После этого модель составляет ответ на русском. Прямого доступа к БД у неё нет.

Доступны ровно пять инструментов: `create_task`, `get_tasks`, `complete_task`,
`update_task`, `delete_task`. Несколько вызовов в одном ответе модели исполняются
через `asyncio.gather`; у каждого запроса своя `AsyncSession`. Цикл ограничен
пятью запросами к модели; если лимит исчерпан, бот предлагает проверить `/tasks`.
Успешные изменения сохраняются сразу: последующая ошибка Groq их не откатывает.

Pydantic-модели одновременно описывают JSON Schema инструментов и валидируют
входные данные. Неизвестные поля запрещены, включая `telegram_user_id`:
доверенный ID поступает только от Telegram handler. Все пользовательские запросы
репозитория фильтруются по этому ID; отдельная общая выборка напоминаний доступна
только scheduler. Заголовок ограничен 200 символами, описание — 2000.

Поиск сначала проверяет точное совпадение без учёта регистра, затем подстроку.
При нескольких совпадениях ничего не меняется, возвращается `ambiguous` со
списком кандидатов. Поиск учитывает и завершённые задачи, поэтому повторное
завершение возвращает `already_completed`. Для пустого результата — `not_found`.

В начале каждого LLM-запроса передаётся `Current local datetime` и часовой пояс.
Python требует ISO 8601 с UTC-offset и переводит даты в UTC. PostgreSQL хранит
их в `TIMESTAMP WITH TIME ZONE`. Относительные даты интерпретируются в `TIMEZONE`.
Сроки в ответах ИИ и `/tasks` отображаются по Москве: `17.10.2026 в 18:00 МСК`,
без ISO-строк, секунд и долей секунды. Backend передаёт модели готовое поле
`deadline_display` и дополнительно форматирует ISO-даты в её ответе.
«В 6 часов вечера» означает 18:00 без дополнительного уточнения. Если указана
только дата, бот спрашивает время напоминания вместо назначения конца дня.
Фильтр на день — полуинтервал от местной полуночи до следующей полуночи.

## Напоминания до срока

APScheduler проверяет расписание каждые `REMINDER_CHECK_MINUTES` минут.
По умолчанию — каждую минуту; допустимые значения — от 1 до 15. Чтобы изменить
частоту, добавьте в `.env`, например, `REMINDER_CHECK_MINUTES=2` и пересоздайте
контейнер бота. Это частота проверки, а не период отправки одинаковых сообщений.

Напоминания идут от дальних отметок к ближним:

- За целое количество суток: за 5, 4, 3, 2, 1 день и так далее в зависимости
  от того, насколько далеко срок. Здесь день — ровно 24 часа до срока,
  а не отправка в полночь. Для срока в 18:00 ежедневные напоминания тоже в 18:00.
- В последние сутки: за **12 часов → 3 часа → 1 час → 15 минут**.
- В момент срока и после него дополнительных уведомлений нет.

При создании задачи или переносе срока выбирается только следующая отметка,
которая ещё впереди. Уже наступившие отметки пропускаются, сообщения за них
не отправляются немедленно. Например:

| Сколько осталось при создании | Последующие напоминания |
| --- | --- |
| 3 дня 2 часа | За 3, 2, 1 день, затем за 12 ч, 3 ч, 1 ч и 15 мин |
| 20 часов | За 12 ч, 3 ч, 1 ч и 15 мин |
| Ровно 1 час | Только за 15 мин |
| 40 минут | Только за 15 мин |
| 10 минут или срок уже прошёл | Напоминаний нет |

В БД хранится `next_reminder_at`. После успешной отправки сохраняется время
следующей будущей отметки; после последней `reminder_sent=True` означает, что
расписание исчерпано. Бот сообщает название, срок в МСК и фактическое оставшееся
время. Напоминание придёт на ближайшей проверке после отметки: обычная задержка
до `REMINDER_CHECK_MINUTES` минут плюс время доставки Telegram. Для отметки
за 15 минут рекомендуется оставить проверку раз в минуту.

После простоя бот отправляет максимум одно запоздавшее напоминание на задачу,
если её срок ещё не наступил, затем переходит к следующей будущей отметке.
Все пропущенные стадии подряд не рассылаются. После срока задача остаётся
незавершённой, но её уведомления прекращаются. За цикл обрабатывается до 100 задач;
при большой очереди возможна дополнительная задержка.

При переносе или удалении срока расписание пересчитывается; изменение названия
или приоритета его не сбрасывает. Завершённые и удалённые задачи не уведомляются.
При временной ошибке отправка повторяется в следующем цикле. Если пользователь
заблокировал бота, уведомления прекращаются для этого срока.

При первом старте новой версии поле расписания автоматически добавляется к
существующей таблице, а будущие напоминания старых незавершённых задач
планируются от времени обновления. Удалять БД или volume не нужно.

## Структура

Ровно **7 Python-файлов**, без дополнительных пакетов и Python-файлов тестов:

```text
hse/
├── config.py
├── database.py
├── repository.py
├── task_service.py
├── llm_service.py
├── bot.py
├── main.py
├── requirements.txt
├── .env.example
├── .gitignore
├── .dockerignore
├── Dockerfile
├── docker-compose.yml
└── README.md
```

| Файл | Ответственность |
| --- | --- |
| `config.py` | Environment, проверка секретов, PostgreSQL URL и timezone. |
| `database.py` | Engine, фабрика async-сессий, ORM User и Task, создание таблиц. |
| `repository.py` | Только SQL-запросы, изоляция пользователей, выборка напоминаний. |
| `task_service.py` | Валидация, поиск и бизнес-операции, структурированные результаты. |
| `llm_service.py` | Groq, схемы пяти tools, agent loop, обработка ошибок. |
| `bot.py` | Router aiogram, команды, текстовые сообщения и ошибки Telegram. |
| `main.py` | Сборка зависимостей, запуск, scheduler, закрытие ресурсов. |

## Ручная проверка 10 сценариев

Перед проверкой запустите Compose, откройте личный чат. Время проверяйте в
`TIMEZONE` приложения. После каждой операции можно свериться с `/tasks`.

| № | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | «Добавь задачу сделать лабораторную завтра в 18:00» | Одна задача, правильная завтрашняя дата и местное время. |
| 2 | «Добавь на завтра купить продукты и закончить проект» | Две новые задачи; модель может вызвать tools вместе или последовательно. |
| 3 | «Что у меня завтра?» | Только задачи со сроками в завтрашнем дне. |
| 4 | «Я сделал лабораторную» | Единственное совпадение завершено и исчезло из `/tasks`; повтор даёт сообщение, что она уже завершена. |
| 5 | «Перенеси задачу купить продукты на пятницу в 15:00» | Тот же ID, новый срок; расписание напоминаний пересчитано. |
| 6 | «Сделай задачу купить продукты важной» | Приоритет `high`, виден в `/tasks`. |
| 7 | «Удали задачу купить продукты» | Задача исчезла; повторное удаление сообщает, что она не найдена. |
| 8 | «Привет, что ты умеешь?» | Короткий ответ без изменений задач. |
| 9 | Создайте «Лабораторная по Python» и «Лабораторная по математике», затем «Удали лабораторную» | Уточнение со списком кандидатов; обе задачи остаются. Повторите с конкретным ID. |
| 10 | При достижении лимита Groq отправьте текст, затем `/tasks` | Текст получает сообщение о перегрузке, `/tasks` продолжает работать. Не нужно намеренно расходовать квоту: HTTP 429 также можно воспроизвести временным mock-клиентом вне проекта. |

Дополнительно:

- Напишите «17 октября пойти на тренировку», затем после вопроса о времени —
  «18:00»: бот должен связать уточнение с тренировкой и создать одну задачу.
- «17 октября в 6 часов вечера пойти на тренировку» уже содержит точное время:
  18:00. В подтверждении и `/tasks` проверьте формат `17.10.2026 в 18:00 МСК`.
- Создайте две похожие задачи, попросите удалить по общему названию, затем
  ответьте «вторую»: бот должен использовать список из предыдущего ответа.
- Создайте задачу на 16 минут вперёд: примерно через минуту наступит отметка
  «за 15 минут». На ближайшей проверке придёт одно сообщение; следующие циклы
  и наступление срока его не дублируют.
- Создайте задачу на час вперёд: немедленного уведомления нет, оно придёт
  примерно через 45 минут, за 15 минут до срока.
- Откройте бота со второго Telegram-аккаунта: список пуст, изменение чужого ID
  сообщает, что задача не найдена.
- «Покажи завершённые задачи» возвращает завершённые, `/tasks` — только активные.
- Удаление срока: «Убери срок у задачи с ID …»; задача остаётся без напоминаний.
- Перезапустите Compose: задачи сохраняются, уже отправленные напоминания не повторяются.

## Проверки и ограничения

Базовые проверки из каталога проекта:

```bash
python -m compileall -q .
python -c "import config, database, repository, task_service, llm_service, bot, main"
docker compose config --quiet
```

Для проверки Compose должен существовать `.env` (для проверки структуры достаточно
копии `.env.example`). Для реального запуска оба API-секрета должны быть заполнены.

В целях простоты ORM-модели находятся в `database.py`, Pydantic-модели и схемы
аргументов — в `task_service.py`, напоминания — в `main.py`. Это позволяет оставить
семь понятных модулей без `models.py`, `schemas.py` и вспомогательных пакетов.

Постоянная история диалога, система миграций, постраничная выдача и распределённый
scheduler не реализованы. `create_all` создаёт таблицы; для нового поля
`next_reminder_at` предусмотрено отдельное автоматическое обновление старой схемы.
Напоминания не гарантируют exactly-once: авария между отправкой в Telegram и
сохранением флага может привести к повторной доставке. Изменение задачи во время
отправки также может пересечься с напоминанием. Параллельные операции не образуют
общую транзакцию, и изменения одной задачи лучше делать последовательно.
Часовой пояс общий для всех пользователей. Интерпретация текста зависит от модели;
backend проверяет аргументы и права, но не может гарантировать семантику LLM-ответа.
